# Journal Report Tool

A standalone, no-AI-required tabbed local report built from `journal.duckdb` — restructured from an earlier single-file version into a small site (one HTML fragment per topic under `tabs/`, loaded into a single tabbed shell app) specifically so it can grow into a dashboard later without a rewrite: adding a new analysis area is "write one more `page_<topic>.py` module," not "copy-paste and rewire everything." Delivered to the user as individual `.py` files (not zipped for now, to make quick edit/redeliver rounds like the ones below faster — package into `journal_report_tool.zip` again once the tool is stable).

Runs entirely locally: `pip install duckdb pandas "plotly==5.24.1"` then `python build_report.py`, no network calls, no API keys. As of the tabbed-shell-UI round below, actually using it (specifically its Refresh button) means serving the output with `python serve_report.py` rather than opening the HTML file directly — see that round for why. See the bundled `README.md` for full setup/run/extension instructions — this doc covers the design decisions and validation, not day-to-day usage.

## Architecture

- **`journal_common.py`** — one shared data-loading pass: session summary, event categorization, ship attribution, latest-loadout parsing, per-ship usage evidence, and the `MODULE_ROLE_HINTS` module-role classifier used by the fit-vs-usage table (see the hpt_ prefix bug below). Also defines `CATEGORY_COLORS` — one fixed color per activity category, shared by every chart/panel in the report — and `is_real_ship()` (see the fleet-usage-overview section below), which excludes SRVs/on-foot suits from ship-only views. Every page module consumes the same prepared `data` dict rather than re-deriving any of this. `load_data()`'s `ship_ev` query also carries `source_file` on every row (added in the Session Spotlights round below), so downstream code can filter the already-loaded event table in pandas instead of re-querying DuckDB for a subset of sessions.
- **`journal_deepdive.py`** — a second shared computation pass (added in the deep-dive round below), run once via `data.update(compute_deep_dive(data))` right after `load_data()`. Computes real flight-hours/distance, docking-leg distances, event tempo, combat/opponent/death/interdiction/near-death evidence (now vehicle-state-filtered fleet-wide — see the vehicle-state-fix round below), kills/deaths by ship split NPC vs. player vs. self-inflicted/accidental (see the self-inflicted-deaths round below), mining-vs-trading economy figures, per-session credits-vs-duration "success" data, exploration/novelty findings plus a discovery-type x primary-star-type hit-rate crosstab (see the exploration-hypothesis-table round below), SRV/on-foot vehicle-state spans correlated against active-mission windows (added in the surface-activity round below), and (added in the Session Spotlights round below) a per-session spotlight computation for the top 5 most lucrative sessions — ships flown, systems visited, category mix, credit-source breakdown, combat-opponent and exploration detail, and carried-over-credit detection — all consumed by the eight tabs below. Contains `filter_real_ships()` (a shared empty-DataFrame-safe version of the real-ship filter) and a `has_star_system_col` guard for databases with a simpler `events` schema (see the deep-dive bugs section). Documented in-code, as a standing lesson from the Session Spotlights round's OOM bug (below), that this is one very long function whose many large intermediate DataFrames are never garbage-collected until it returns — any future addition here should prefer reusing an already-computed dataframe over adding a fresh full-table query late in the function.
- **`journal_page_utils.py`** — shared page writer for each tab's fragment: embeds the plotly.js bundle once per fragment so it stays independently openable (e.g. for debugging outside the shell), wraps each chart in a spaced container div, and provides `chart_with_hover_table()` (see below) for pairing a chart with a custom color-coded side panel instead of Plotly's native legend/tooltip. `write_page()`'s `figs` list also accepts a raw HTML string alongside plotly Figures (used for the star-type hit-rate table — see the exploration-hypothesis-table round below), as long as `figs[0]` is still a real Figure (needed to embed the plotly.js bundle). `include_nav` defaults to `False` as of the tabbed-shell-UI round below — the shell's own left-side tab bar replaced the old per-fragment top nav bar, which would otherwise show a redundant second nav strip inside every tab's iframe; `NAV_LINKS` here is now the single canonical tab list the shell itself is generated from, so a new tab still only needs one line added here (see build_shell() below).
- **`page_gameplay.py`** → tab **Gameplay Analysis** (`tabs/gameplay_analysis.html`) — when/how often you play, overall activity mix over time (all ships combined, chart + side panel), session-length distribution, dropdown event-type explorer.
- **`page_ships.py`** → tab **Ship Profile Analysis** (`tabs/ship_profile_analysis.html`) — fleet usage overview (bar chart, idle-ship table, activity-coverage table — see below), kills-by-ship and deaths-by-ship (NPC vs. player vs. self-inflicted/accidental — see the vehicle-state-fix and self-inflicted-deaths rounds below), per-ship activity composition (parallel comparison bar, category-colored), per-ship activity-over-time (dropdown drill-down, chart + side panel), and a fit-vs-usage findings table (see below).
- **`page_play_patterns.py`** → tab **Play Patterns** (`tabs/play_patterns.html`) — event tempo by category, session duration vs. net credits (kept as two separate axes, not blended into one score), and a per-category "which activity actually pays / lasts longest" table (added in the deep-dive round below). Its "top 5 most lucrative sessions" list is the same one the Session Spotlights tab (below) drills into.
- **`page_combat.py`** → tab **Combat Analysis** (`tabs/combat_analysis.html`) — opponent mix fleet-wide and per-ship, every recorded ship-combat death with an "overconfidence" flag, interdiction exposure, near-death (sub-25%-hull) events by ship (added in the deep-dive round below; vehicle-state-filtered as of the vehicle-state-fix round below; self-inflicted/accidental deaths correctly excluded as of the self-inflicted-deaths round below, since they aren't combat).
- **`page_economy.py`** → tab **Economy Analysis** (`tabs/economy_analysis.html`) — trading vs. mining credits-per-hour, top commodities for each, best-earning ship per activity, with an explicit mining/trading double-counting fix (added in the deep-dive round below).
- **`page_exploration.py`** → tab **Exploration Deep Dive** (`tabs/exploration_deep_dive.html`) — most profitable systems for exploration/exobiology data, first-discoveries by category, rare stellar phenomena and other outlier findings (added in the deep-dive round below), and a discovery-type x primary-star-type hit-rate table testing whether star type at arrival predicts high-value planets, pristine rings, and biological finds (added in the exploration-hypothesis-table round below).
- **`page_surface_activity.py`** → tab **Surface Activity** (`tabs/surface_activity.html`) — SRV and on-foot time, split into "in service of" an active mission vs. freely player-chosen, and what that time is actually spent on (added in the surface-activity round below).
- **`page_session_spotlights.py`** → tab **Session Spotlights** (`tabs/session_spotlights.html`) — a per-session deep dive on the top 5 most lucrative sessions: ship(s) flown, systems visited, predominant events, what actually earned the credits (mission reward vs. opportunistic combat/trade voucher vs. a bulk exploration/exobiology data cash-in), a combat-opponent or exploration breakdown depending on what the session was, and a check for whether a bulk-data credit total was earned in-session or just cashed out from data/samples banked earlier (added in the Session Spotlights round below).
- **`page_after_action.py`** → `after_action.html` (planned, not built yet) — see the After-Action Analysis section below.
- **`build_report.py`** — entrypoint: loads data once, calls each page module (writing into `tabs/`), builds the Overview tab, and (as of the tabbed-shell-UI round below) generates `index.html`, the tabbed shell app itself. Also runs a self-check (`_sync_stale_downloads()`) before importing any of this tool's own modules, recovering automatically from the recurring "re-delivered file landed as `-1` instead of overwriting" collision bug — see that round's write-up below.
- **`serve_report.py`** (new in the tabbed-shell-UI round below) — a small local HTTP server: serves the built report with no-cache response headers, and exposes `POST /api/rebuild` (reruns `build_report.py` as a subprocess) for the shell's Refresh button. Not required to view the report (opening `index.html` directly still works, read-only), but required for Refresh to actually do anything.

## Category refinement: transit vs. deep exploration

Prompted by the user noticing trading ships showed an outsized "Exploration" share — caused by routine FSS pings during transit between trade stations getting counted the same as genuine exploration effort. Fixed properly rather than approximately: the journal's `Scan` event carries a real `ScanType` field (`AutoScan` vs `Detailed`/other), so categorization now splits on that directly — `Exploration (transit)` for passive/automatic scanning, `Exploration (deep)` for deliberate scans, exploration-data sales, exobiology, etc. This is a precise signal from the data itself, not a heuristic guess. Real data ends up with 12 non-ambient categories (Colonisation, Combat, Engineering, Exploration (deep), Exploration (transit), Mining, Other, Passengers/Missions, Ship management, Social, Trading, Travel) — relevant to the hover-tooltip saga below, since that category count is what broke several fix attempts before landing on the actual solution.

## Fit-vs-usage findings table (ship_profile_analysis.html)

Answers the actual goal behind this line of inquiry: not just "what does this ship do" but "does its current fit match what it actually does, so I can stop A-rating everything and trim non-purpose modules." For each ship's most recent `Loadout`, a conservative, hand-picked set of module types is matched by internal Elite item-name substring (`MODULE_ROLE_HINTS` in `journal_common.py`), then cross-checked against that ship's actual behavioral evidence (combat-event count, `FuelScoop` event count, deep-exploration event count). A module gets flagged "likely unnecessary" (zero supporting evidence) or "worth reviewing" (evidence present but rare, under a documented threshold). Every row prints the raw `Slot`/`Item` string alongside the flag, so a wrong guess is checkable rather than taken on faith — explicitly scoped as a heuristic screen, not an authoritative verdict, and it does **not** compute an optimal replacement fit (that needs the Coriolis engineering-modifier math from `ship-build-advisor.md`, not built yet).

## A real bug caught before delivery: ship misattribution

Initial implementation fetched the categorized-events table and the ship-attribution ASOF-join result as two **separate** DuckDB queries, then joined them in pandas by raw positional `.values` assignment. This silently misattributed events to the wrong ships — DuckDB does not guarantee matching row order across two independently-executed queries with no `ORDER BY`. Caught via a purpose-built synthetic test (three ships with deliberately distinct, non-overlapping behavioral signatures — a trader, an explorer, a combat ship — each given a piece of evidence the others should have zero of) *before* this reached the user: cross-checking the derived per-ship evidence counts against the synthetic ground truth showed a trading-only ship with nonzero fuel-scoop and deep-exploration counts it should never have had. Fixed by doing the categorization and ship attribution as a single query, so row correspondence is guaranteed rather than assumed. Re-validated afterward: exact match between derived evidence and synthetic ground truth for all three ships, and the fit-vs-usage table correctly flagged only the deliberately-overfitted trading ship (4 findings: shield generator, fuel scoop, two hardpoint-mounted weapons) while the correctly-fitted explorer and combat ship came back clean.

## Hover/legend saga: five rounds, from "give it more room" to a real side panel

User-reported: on `gameplay_analysis.html`, hovering the "Activity mix over time" chart (a multi-category stacked-area chart) showed a popup covered by the heatmap chart directly above it, near the top of the chart.

**Round 1 (incomplete — validated only against thin synthetic data):** `hovermode="x unified"` renders one tall tooltip box (one line per category) anchored near the hovered point. Fix: CSS gap between charts + top margin inside the chart. Verified only against a 4-category synthetic dataset — worked there, looked done. Broke at real scale: real data has 12 categories, and the tooltip's height scales with category count, so a margin sized for 4 lines did nothing for 12.

**Round 2 (still incomplete — passed a narrow spot-check, failed in real use):** `hovermode="x"` instead of `"x unified"`, on the theory that separate per-category boxes wouldn't scale the same way. They still cluster into one contiguous stack — same underlying problem. A narrow spot-check didn't reproduce it; real use did.

**Round 3 (fixed the size problem, but lost information the user wanted):** `hovermode="closest"` — one small box at a time, tooltip size independent of category count. Verified clean everywhere. But this also dropped the "see every category's share at a glance" feature the chart exists for. User: not what they wanted.

**Round 4 (structurally correct hover content, wrong presentation):** Replaced Plotly's native tooltip entirely with a custom HTML table rendered **below** the chart, driven by `plotly_hover`/`plotly_unhover` JS events — real month header, Category/percentage columns, sorted highest-first, native tooltip box hidden via CSS (`hoverinfo="none"` doesn't work here since `px.area`'s auto-set `hovertemplate` overrides it; a transparent `hoverlabel` color rendered as solid black in the browser regardless of what the figure's JSON said — both discovered by testing against real rendered output, not by trusting config values). Two real bugs caught in this round: an apostrophe in placeholder text breaking a single-quoted JS string (fixed by routing every Python string into JS via `json.dumps()` rather than raw f-string interpolation, after this string-escaping problem had already bitten once); and the transparent-hoverlabel dead end just mentioned. Verified thoroughly against the real database — table populated correctly, zero JS errors. User's reaction: still not the right presentation — "a separate table that pops into view below the chart" wasn't a hover/popup at all, and asked instead for the table to live beside the chart, in place of the legend, with rows colored to match categories.

**Round 5 (the actual fix — a side panel, replacing the legend, not a popup):** `chart_with_hover_table()` in `journal_page_utils.py` now lays the chart and a table side by side in a flex row (chart ~75% width, panel ~240–280px fixed), not stacked. The panel doubles as the chart's legend: `showlegend=False` on the figure, and the panel shows the full, fixed-order category list with a color swatch per category at all times — "–" for the value column when idle, replaced with live percentages (still in the same fixed row order, so it never reshuffles) when hovering, via the same `plotly_hover` event mechanism from round 4. Colors are now a single shared `CATEGORY_COLORS` map in `journal_common.py` (one hex color per category), applied via `color_discrete_map`/explicit trace `line.color` to every category-colored chart in the report (the fleet-wide activity-mix chart, the per-ship activity-mix chart, the ship-composition bar chart, and the new fleet-usage-overview bar chart below) — so a category is the same color everywhere, not just within one chart, and the panel's swatches genuinely match what's drawn.

A third real bug, specific to the side-by-side layout, caught by testing rather than assumed: **the chart rendered too wide and visually overpainted the panel**, even though the panel's own bounding box measured correctly (280px, positioned to the right). Root cause, found by comparing the chart div's measured CSS width (896px, correct) against its inner `<svg>` element's actual `width` attribute (1200px, wrong): the browser executes a Plotly figure's inline sizing `<script>` synchronously *while parsing* the page, which happens **before** the script reaches the panel's sibling `<div>` later in the same HTML string — so at the exact moment Plotly measures its container to decide the SVG's size, the flex row briefly has only one child, and Plotly sizes the chart to fill the full available width, then never re-measures once the panel is added a moment later and the flex row narrows the chart's real container. `config={"responsive": True}` was tried first and did **not** fix it — that setting reacts to the browser window resizing, not to the chart's own container settling to a different size without a window resize, so it never fired here. The actual fix: an explicit `Plotly.Plots.resize(gd)` call inside the panel's own `<script>` block, which runs after both flex children already exist in the DOM (so the layout has settled by then) — verified by checking the SVG's `width` attribute directly before and after (1200 → 896, matching its container).

Verified end to end against the real 2,018,910-event / 12-category database on both pages (`page_gameplay.py` fig3, `page_ships.py` fig7): chart and panel sit side by side at matching heights, SVG width matches its container (no overpainting), idle state shows the full color-coded category list, hovering populates real percentages in the same fixed order with a correct month/ship header, unhovering reverts cleanly, zero JS console errors, and colors match between chart and panel. Screenshotted for visual confirmation, not just measured. Re-ran the synthetic ship-attribution/fit-vs-usage ground-truth test afterward — exact match, unchanged.

**Lesson for future validation on this tool, now stated plainly because it took five rounds to land:** rounds 1–2 failed because a fix that works by giving Plotly's native tooltip "enough room" for *variable-length* content doesn't generalize. Round 3 was the reminder that removing a size-dependency can also silently remove a feature the user needed. Round 4 got the content right (a real table, not a native tooltip) but not the presentation the user actually wanted (beside the chart as a legend, not a popup below it) — a reminder that "technically correct and well-tested" isn't the same as "what was asked for," and it's worth restating the request back in concrete terms before building the next iteration rather than after. Round 5's layout bug is a reminder that a side-by-side flex layout with inline `<script>`-based content (like Plotly's own output) can have real script-execution-order bugs that only show up in the rendered DOM, not in the figure's JSON or the container's measured CSS box — the SVG's own `width` attribute was the tell, not the div's bounding box. Any future layout/rendering fix on this tool: verify against the real 1,559-session database, check what was actually asked for (not just "does this technically work"), and when a chart's rendered content might not match its container, check the drawn element's own attributes, not just the container's measured size.

## User-caught bug: heat sink launchers (and other utility mounts) mislabeled as weapons

The user, reading the fit-vs-usage table, noticed heat sink launchers showing up as "Hardpoint-mounted module" and asked why — heat sink launchers are utility-slot items (fire-group/key-bound, not a weapon), not hardpoint weapons.

Root cause: Elite's internal item naming uses the `hpt_` prefix for **both** actual weapon hardpoints and utility-mount items — utility mounts are, internally, just the smallest hardpoint size class, not a separately-named family. `MODULE_ROLE_HINTS`'s original catch-all `("hpt_", "Hardpoint-mounted module")` rule had no way to distinguish them by name alone, so it caught heat sink launchers too. This fed directly into a wrong conclusion in the fit-vs-usage table: the rule that flags a hardpoint module with zero combat evidence as "likely an unnecessary weapon" doesn't apply to a heat sink launcher at all (not a weapon; its actual usage isn't measured by combat-event counts, which only cover `UnderAttack`/`Died`/`Interdicted`/etc.).

Checking further (not just the one item the user named) found the same bug affects several other common utility-mount items sharing the `hpt_` prefix — most importantly **shield boosters** (49 instances across the real fleet, vs. 19 heat sink launchers), plus chaff launchers (24), kill warrant scanners (16), and others. A shield booster with zero combat evidence being labeled "likely an unnecessary weapon" would have been a materially misleading flag for a lot of ships, not just a cosmetic mislabel.

Fix: added specific substring matches for the known utility-mount item families (heat sink launcher, shield booster, chaff launcher, electronic countermeasure, caustic sink launcher, point defence turret, kill warrant scanner, manifest scanner) to `MODULE_ROLE_HINTS`, ordered *before* the generic `hpt_` fallback (first match wins in `_module_role()`), so only genuinely unrecognized hardpoint items — actual weapons — still fall through to the generic "Hardpoint-mounted module" label the combat-evidence rule is meant for. These utility items now get their own role labels and are simply not covered by any `FLAG_RULES` entry (no new heuristic was invented for them — that would need usage evidence this tool doesn't currently track, e.g. `HeatWarning`/interdiction-evasion events for heat sinks or shield-down events for boosters, and wasn't asked for).

Verified against the real database: re-ran `_module_role()` over every ship's latest loadout and confirmed all 19 heat sink launchers, 49 shield boosters, 24 chaff launchers, and 16 kill warrant scanners now get their correct specific label instead of "Hardpoint-mounted module," and confirmed none of them appear in the fit-vs-usage findings table anymore (since no flag rule references their new labels). Re-ran the synthetic ship-attribution/fit-vs-usage ground-truth test — exact match, unchanged (the synthetic test's fixtures don't include these item types, so this was purely a no-regression check).

## Fleet usage overview (ship_profile_analysis.html): "which ships should I sell or refit?"

User's request: a visualization for overall ship usage, specifically to spot ships that are almost never used (candidates to sell/store) or that could be refitted to cover an activity the fleet currently handles poorly. A pie chart was considered and rejected in favor of three complementary views, since a single pie can't carry "how much," "how long untouched," and "is this activity covered" at once, and 30+ ships makes a pie's wedges unreadable at the low end (exactly where the useful signal — the barely-used ships — lives):

- **Fleet usage bar chart** (`fig_usage`) — every real ship, horizontal bars, log-scale total event count (linear would compress everything under a heavily-used main ship into invisibility), colored by that ship's single most common (dominant) activity category using the same shared `CATEGORY_COLORS` map as the rest of the report. Sorted by total events, so the long tail of rarely-touched ships is immediately visible at the bottom.
- **Idle-ship table** (`fig_idle`) — every ship, sorted longest-untouched first: total events, dominant activity, last-active date, and days idle (computed against the database's own most recent timestamp, not "today," so re-running the report later doesn't silently inflate every idle count from the report-generation date itself). This is the direct "should I sell this" list the user asked for.
- **Activity coverage table** (`fig_coverage`) — per category, the single ship contributing the largest share of that category's events, and what share that is. Categories where no ship exceeds a 25% concentration threshold are flagged "No dedicated ship — spread across the fleet" (highlighted row) — this is the "which activity doesn't have a good ship for it yet" half of the user's question, i.e. a candidate activity to refit an idle ship toward. On the real fleet: 5 of 12 activities (Exploration (transit), Social, Travel, and others) have no concentrated ship; Combat, Ship management, Other, and Mining each have a clear primary ship (up to 71% concentration for the dedicated mining ship).

Both new tables and the description text are explicit that this is a **signal, not a verdict** — dominant-activity coloring is the single largest category by event count, not a judgment on whether that's the ship's "intended" role, and a ship can be legitimately low-event but still valuable (e.g. a rarely-flown but expensive exploration ship kept for one specific long-range trip).

### Bug caught while building this (not user-reported): SRVs and on-foot suits counted as "ships"

While building the fleet-usage bar chart, a direct query against the `ship_display` view showed entries like `TestBuggy [42]` and `UtilitySuit_Class2 [4293000006]` mixed into the ship list. Root cause: SRVs (`TestBuggy`) and on-foot suits (`UtilitySuit_Class*`, `ExplorationSuit_Class*`, `TacticalSuit_Class5`) also emit `Loadout`/`LoadGame` events carrying a `ShipID`, so the existing ship-attribution pipeline — built for actual starships — swept them in too. This wasn't a new bug (the existing fig6/7/8 ship-composition charts had the same contamination) but became actively misleading here specifically, since this feature's entire point is "should I keep or get rid of this," and an SRV or suit showing up as a sell/refit candidate is nonsensical.

Fix: added `is_real_ship()` to `journal_common.py` — excludes any ship whose display name contains `testbuggy`, `utilitysuit`, `explorationsuit`, or `tacticalsuit` (case-insensitive). This is a safe substring check specifically because these vehicle types never get a custom in-game name (no `ShipName` field is ever set for them), so they always render via the fallback `"{type} [{ident_or_id}]"` pattern the check targets — a real starship the user has actually named won't accidentally match. Applied only to the three new fleet-overview computations (`page_ships.py`), deliberately **not** to the existing `active`/`ship_ev` data used by fig6/7/8, to avoid changing previously-validated behavior the user hadn't asked to revisit. Verified: the real fleet's ship count for this feature dropped from 51/52 (including SRV/suit entries) to 34 real ships, with no `TestBuggy`/`UtilitySuit_Class*` text visible anywhere in the new tables' extracted content.

### Bug caught while screenshotting (not user-reported): a ship named a single space renders as a blank row

Visual (not just text-extraction) verification of the idle-ship table turned up one row with a completely blank ship name — easy to mistake for a rendering bug. Root cause: one real ship's custom `ShipName` in the journal data is literally a single space character (`" "`) — presumably an accidental in-game rename. The existing `NULLIF(ship_name, '')` guard only catches an *exactly empty* string, so a whitespace-only name survived as "real," and the fallback-to-`type [ident]` display logic never triggered for it.

Fix: changed the `ship_name` extraction in `journal_common.py`'s `ship_changes` view to `NULLIF(TRIM(...), '')` — trimming before the empty-check means a whitespace-only name is now treated the same as a genuinely empty one and falls through to the `"{type} [{ident}]"` display fallback, same as any ship with no custom name at all. This affects display everywhere `ship_display`/`display_name` is used (all pages), not just the new fleet-overview tables, since it's a correctness fix to the shared name-resolution logic, not a new filter scoped to one feature. Verified: the previously-blank row now reads `belugaliner [JA-02B]`; re-ran the synthetic ground-truth test afterward — exact match, unchanged (the synthetic fixtures don't include a whitespace-only name, so this was purely a no-regression check).

Screenshot-verified (not just text-extracted) all three new sections against the real database: the bar chart renders 34 correctly-colored, log-scale bars with a legend; the idle-ship table is fully populated with real ship names, dates, and idle-day counts, longest-idle first; the activity-coverage table correctly highlights the 5 under-covered categories. Zero JS console errors; plotly-div count on the page went from 3 to 6 as expected.

## Deep-dive round: real flight-hours/distance, plus four new pages (combat, economy, play patterns, exploration)

Triggered directly by the user pushing back on the fleet-usage-overview round: "Can Battle of Grunwald really be my most often used ship? ... Worth The Weight is not my predominant travel ship ... Maybe the definition of Travel needs tuning." The complaint was correct and diagnosable from the data itself: raw event counts are a badly biased proxy for "usage," because different activities emit events at wildly different rates — Combat emits roughly 80–137 events per active hour, Travel roughly 24–31, Passengers/Missions roughly 1.8–4.5. A combat-heavy ship racks up event counts an order of magnitude faster than a travel-heavy one doing the same amount of real playtime, so "most events" was really measuring "flies through the most combat," not "flown the most." The user then asked for a much larger buildout in the same message: real time-in-ship and distance-travelled per ship, distance between docking events, event tempo per hour/session, and — explicitly inviting broad scope — combat opponent/survivability analysis, trading-vs-mining profitability, session "success" kept as two separate axes (credits earned vs. session duration, not blended), exploration profitability by system, and novelty/outlier findings.

**Real usage metrics.** `per_ship_flight` computes actual flight-hours from contiguous same-ship, same-session timestamp spans (a SQL window-function group-id, materializing `LAG(ship)` in one CTE before computing the running `SUM(...)` group id in a second, since DuckDB rejects nested window function calls in one SELECT). `per_ship_distance` sums `FSDJump`'s own `JumpDist` field (real light-years, not an event-count proxy) per ship. The fleet-usage bar chart and idle-ship table on `ship_profile_analysis.html` now use these instead of raw event counts, plus a new light-year bar chart. Result: Quo Vadis (111,400 ly) and Jumping To Conclusions (105,436 ly) are now correctly shown well ahead of Worth The Weight (6,752 ly) — confirming the user's suspicion that a heavy cargo hauler doing a lot of *events* per trip isn't the same as covering the most distance.

**Play Patterns** (`play_patterns.html`, new): event tempo by category (the ~80–137 vs. ~24–31 vs. ~1.8–4.5 events/hour figures above, now shown directly rather than left implicit), a session duration-vs-net-credits scatter (kept deliberately as two separate axes per the user's explicit instruction not to blend "fun" and "reward" into one score — correlation is weak, `duration_credit_corr ≈ 0.16`, `duration_rate_corr ≈ -0.02`, supporting that framing), and a per-category table of which activity actually pays best per hour and per session.

**Combat Analysis** (`combat_analysis.html`, new): bounty-kill opponent mix fleet-wide and per-ship (from `ShipTargeted`/Bounty evidence), every recorded ship-combat death (on-foot/SRV deaths excluded) with an "overconfidence" flag — a deliberately narrow, checkable signal: a ship whose usual role isn't combat getting destroyed in ship-to-ship combat anyway, not a general vibes-based judgment — interdiction exposure by ship, and near-death (hull dropped below 25%) events by ship as a danger proxy independent of actual losses.

**Economy Analysis** (`economy_analysis.html`, new): trading vs. mining credits-per-hour, top commodities for each, and best-earning ship per activity. A real correctness bug was caught and fixed here before this ever reached the user — see below.

**Exploration Deep Dive** (`exploration_deep_dive.html`, new): most profitable systems for exploration-data and exobiology sales, first-discoveries by Codex category, and an "unusual observations" section (Thargoid Codex entries, rare stellar phenomena visited, and an explanation of a $3.09B single-session outlier — see below).

### Self-caught bug: mined commodities double-counted as trading profit (~80x overstatement)

While building the Economy page, a first pass credited **all** `MarketSell` revenue for a commodity to "trading profit," including commodities that are actually mostly mined and sold for free input cost (e.g. painite: 10 units ever bought vs. 16,321 sold). This produced an absurd ~$10.8B "trading profit" for painite alone, and an overall trading figure inflated by roughly 80x. Root cause: `MarketSell` doesn't record whether the sold cargo was bought at a market or mined via `MiningRefined` — there's no per-unit provenance in the journal to tell the two apart.

Fix: built a `mined_commodity_norms` set from `MiningRefined`'s own commodity names (normalized for matching) and excluded any commodity in that set from the "pure trade" table entirely — the conservative choice, since there's no way to split a commodity that's legitimately both bought/sold and mined (gold, silver, palladium, platinum, tritium) without guessing. After the fix: trading dropped from the absurd figure to a sane $132.6M, and the real finding survived scrutiny — mining outearns pure trading by roughly 72x per hour in this fleet, a genuinely interesting result rather than an artifact of the bug.

**A second, subtler version of the same bug**, caught only by explicitly reconciling the per-ship trade-profit sum against the fleet-wide "pure trade" total (a technique used throughout this round specifically to catch this class of error): the per-ship computation excluded mined commodities but not the `units_bought > 0` restriction the fleet-wide table also applied, producing a $1.5B per-ship sum against a $132.6M fleet-wide total. Fixed by restricting per-ship buy/sell computation to the exact same commodity set the fleet-wide table used. After the fix, the two sums reconciled exactly (132,605,311 both ways) — and the previously-hidden mismatch turned out to be pointing at something real rather than just a bug: "Worth The Weight" showed a large negative per-ship trade profit (bought $1.8B, sold only $906M on the same hull), indicating cargo bought on one ship and sold from another, most likely via a fleet carrier or a direct ship-to-ship cargo transfer. This is documented as a methodology caveat on the Economy page rather than "corrected away," since per-ship trade profit genuinely does mean "which ship handled this side of the transaction," not a strict per-hull profit-and-loss statement.

### The $3.09B single-session outlier

A session-success query surfaced one session with ~$3.09B in net credits — investigated rather than taken at face value, since it looked implausible next to every other session. Traced to a single `SellOrganicData` bulk cash-in event containing 100+ `BioData` entries — a redemption of exobiology samples banked across many earlier real-world play sessions in one lump sum, not one incredible session of actual play. Documented as a caveat on both the Play Patterns and Exploration Deep Dive pages, alongside the general note that `SellExplorationData`/`MultiSellExplorationData` credit is split evenly across all systems named in a bulk sale (the journal gives no per-system breakdown), so single-system profitability figures there are an approximation.

## Surface Activity round: SRV vs. on-foot time, in service of a mission or not

Follow-up request after the deep-dive round: "Look similarly at SEV and on foot activity. Typically SEV is in service of a mission but sometimes it is exploring. On foot, same. See if you can correlate activities in service of active missions versus strictly player chosen behavior." A new shared computation (added to `journal_deepdive.py`) and a new page, `page_surface_activity.py` → `surface_activity.html`.

**Vehicle-state reconstruction.** Rather than infer whether the player is in the ship, driving an SRV, or on foot from context, a small state machine over five boundary event types tracks it exactly: `LaunchSRV` → SRV, `DockSRV`/`SRVDestroyed` → SHIP, `Disembark` → FOOT, `Embark` → SRV or SHIP depending on that event's own `SRV` flag (Embark/Disembark fire for both ship-foot and SRV-foot transitions, distinguished only by that flag — confirmed by tracing a real session's full event sequence before writing any aggregation code, rather than assuming). Each boundary event's own timestamp starts a span that runs until the *next* boundary event in the same session — a deliberate departure from the flight-hours approach elsewhere in this tool (which infers span duration from the density of events *inside* the span): on-foot events are comparatively sparse, and using interior event density here would have badly undercounted short on-foot excursions with little logged activity in the middle (verified this would matter before committing to the approach, by checking how many boundary-only pairs had zero interior events).

**Mission-window correlation.** A mission's "active" window runs from `MissionAccepted` to the first of `MissionCompleted`/`Failed`/`Abandoned` (covers 99% of missions; the small remainder that never resolves in the journal falls back to its own `Expiry` timestamp as an assumed end). Every SRV/on-foot excursion is checked for time-overlap against every mission window (a straightforward interval-overlap join, not an ASOF join, since multiple missions can be active at once) to classify it as "under an active mission" or "free choice." This is stated on the page as a real limitation: overlap only means a mission was outstanding at the time, not that the SRV/on-foot activity was actually being done for it.

**The finding runs opposite to the question's own framing.** On foot (349h total): 60% overlaps an active mission — heavily settlement missions (reboot/restore, salvage, assassination, onslaught), and 82% of that mission-linked on-foot time is spent on item-handling events (picking up/dropping cargo, data, or loot), not combat or scanning. In an SRV (283h total): only 15% overlaps an active mission — 85% of SRV time is free-choice driving with no mission active, and a striking share of BOTH the free-choice (35%) and mission-linked (69%) SRV time is spent in combat (surface conflict zones/skirmishes), not prospecting or transit between points of interest. In other words: on-foot activity is the one that's mostly mission-tied, and SRV activity is the one that's mostly free-roam combat/collection — the reverse of the user's stated assumption. Presented plainly as a genuine finding rather than something to explain away.

**A handful of on-foot/SRV-specific event types** (backpack/cargo handling, suit swaps, terminal hacks, and the vehicle-transition events themselves) aren't in the shared `CATEGORY_MAP` used everywhere else in the report — deliberately not added there, since they're only meaningful in a foot/SRV context and would just be noise on every other page. A small `SURFACE_CATEGORY_OVERRIDES` dict local to this section of `journal_deepdive.py` handles them (e.g. `BackpackChange`/`CollectItems`/`ShipLocker` → "Looting/Inventory", a page-local category not in the shared `CATEGORY_COLORS` map, given its own color directly in `page_surface_activity.py`).

**A real tz-mismatch bug caught immediately, not shipped**: the first version of the mission-window merge raised `ConversionException: Could not convert 'datetime' to type TIMESTAMP WITH TIME ZONE` on the DuckDB overlap join. Root cause: `end_ts` (from actual `MissionCompleted`/`Failed`/`Abandoned` timestamps, tz-naive from DuckDB) and the `Expiry`-fallback values (parsed from a journal string with a trailing `Z`, which pandas reads as tz-aware UTC) had ended up in the same column with mismatched tz-awareness, making the column `object`-typed rather than a clean `datetime64`. Fixed by parsing `Expiry` as UTC then explicitly stripping the tz (`.dt.tz_localize(None)`) before filling, so the whole `end_ts` column is consistently tz-naive.

Verified against the same pipeline as every prior round: full rebuild against the real database (Playwright: 0 JS errors, 3 plotly divs on the new page, matching the three figures built), screenshot-based visual check of the new page's stacked-hours chart, category-mix chart, and mission-type table, a rebuild against the synthetic fixture (which has zero SRV/on-foot/mission events — the page correctly renders a plain "no SRV or on-foot activity recorded" message rather than erroring, exercising the same empty-DataFrame-safety discipline established in the deep-dive round), and a re-run of `check_table.py` confirming no regression to the fit-vs-usage findings.

## After-Action Analysis (planned feature, not built yet)

Requested directly by the user alongside the SCO/older-ship and unflown-ship notes above: "Make sure the analysis we're doing on historical data can be performed against the log files we generate in the future because the analysis we're doing will become an ongoing sort of monitoring and self-reflection. One of the features we want is an after-action analysis." Two distinct asks bundled together: (1) confirm the existing analysis pipeline isn't quietly assuming today's data is final, so it keeps working correctly as new journal files accumulate; (2) design a feature that actively uses that ongoing accumulation — a periodic "what's new since last time" review, not just a one-time report.

**(1) Verified, not just assumed, this round.** `Grep`-searched the whole `journal_report/` codebase for hardcoded wall-clock/current-date patterns (`2025|2026|today|datetime\.now|date\.today`) — the only matches were intentional, already-correct uses: dated prose describing a historical finding (e.g. the Colonisation-update date in `page_exploration.py`) and a literal patch-date annotation in `journal_common.py` (`("2025-02-26", "Trailblazers (Colonisation)")`, an Elite Dangerous update-history reference value, not a live clock read). No page module computes "idle days" or any other time-since figure against the machine's current date — the fleet-usage-overview round already established the correct pattern (idle-day counts computed against the database's own most recent event timestamp, not "today"), and that pattern held everywhere it was reused. Combined with `data-architecture.md`'s already-documented incremental/idempotent ingestion design (new journal files get appended and re-ingested without reprocessing or duplicating old ones), the pipeline already satisfies "keeps working as new logs arrive" architecturally — this was a confirmation pass, not a fix; nothing needed to change.

**(2) Design sketch for `page_after_action.py` → `after_action.html`, not yet built.** The core idea: rather than a static one-time report, treat each re-run of the tool (as new journal files accumulate between play sessions) as an opportunity to surface *what changed* since the last time the user looked, rather than making them re-read the whole report to spot it themselves.

- **A high-water-mark marker**, mirroring the ETL's own `ingested_files` idempotency pattern from `data-architecture.md` section 3: record the timestamp (or session ID) of the most recent event considered "already reviewed" at the end of each after-action pass, so the next run only needs to analyze the delta rather than the whole 2M+-event history again. Framed explicitly as "since your last review," not "since the report was first built," so it stays useful indefinitely rather than becoming a diminishing one-time novelty.
- **Personal-records-broken framing**: for each metric this tool already computes elsewhere (credits/hour by activity, flight-hours by ship, longest session, biggest single payout, rarest exploration find, etc.), check whether anything in the new delta beat the prior best — and only surface it if it did. Reuses existing computations from `journal_common.py`/`journal_deepdive.py` rather than inventing new metrics; the new part is purely the "did this new data change any record" comparison.
- **New-to-the-journal signals**: first-ever occurrences of an event type, ship type, system, or commodity not seen before this delta — reusing `data-architecture.md`'s already-documented defensive practice of logging unseen event types, rather than building a separate detection mechanism. A new ship type flown for the first time, or a system visited that's never appeared in any prior session, would surface here.
- **Comparison against established per-category baselines** already computed elsewhere in the tool (Play Patterns' events-per-hour-by-category figures, Economy's credits-per-hour figures) — flagging when a new session's per-category rates land well outside the historical range, as a light "this session played differently than usual" signal, not a judgment on whether that's good or bad.
- **A light connection back to `future-aspirations.md`**: where a new delta touches on one of that doc's open items (e.g. a first visit to Rigel, a new colony-chain development, a Powerplay module finally acquired), note it — reusing that doc's existing goal list rather than duplicating it as a second source of truth.

Explicitly scoped as a design only at this point — no code has been written for `page_after_action.py` yet, and it isn't in `build_report.py`'s page list. The next concrete build step is implementing the high-water-mark marker and the personal-records-broken comparison first (the two pieces with the clearest reuse of already-validated logic), before the more open-ended "new-to-the-journal" and baseline-deviation pieces.

## Self-inflicted-deaths round: a third death category, and a second latent misclassification it uncovered

Direct follow-on request right after the vehicle-state-fix round shipped: "Differentiate also deaths caused by self, due to accidental collision with surface or asteroid or something. Unforced errors of a sort." The NPC/player split above only ever recognized two causes; a death with no antagonist recorded at all (a genuine collision, running out of fuel, flying into a star, a fuel-scoop overheat, and the like) fell through the old `death_opponent_type()` classifier's catch-all `return "NPC"` and was silently counted as an NPC kill.

**Checked what the journal actually records before writing a classifier, not assumed.** Read every one of the real database's 62 lifetime `Died` events' raw JSON directly rather than guessing at the schema: 43 have a singular `KillerName` (NPC), 3 have a `Killers` array with `"Cmdr <name>"` entries (player), 4 have only a `KillerShip` with no name at all (`skimmerdrone`/`ps_turretbasesmall_3m`/`ps_turretbasemedium02_6m` — on-foot settlement-defense installations, already correctly excluded from "ship combat" by the pre-existing `ONFOOT` substring list, and correctly still NPC-caused, not self-inflicted), and the remaining **12 have none of Killers/KillerName/KillerShip at all** — no recorded antagonist whatsoever. That 12-event set is the actual signal this data supports for "self-inflicted/accidental" — the journal never records the specific cause (no "collision," "fuel exhaustion," or similar field exists), only that nothing else killed the player, so "Self/Accident" is the most precise label the data can honestly carry, not a guess at what actually happened.

**Fix.** `death_opponent_type()` (in `journal_deepdive.py`) now returns `"Self/Accident"` when a `Died` event has no `Killers` array and neither `KillerName` nor `KillerShip` is present, instead of falling through to `"NPC"`. `deaths_by_ship`/`deaths_by_ship_summary` pick up the new bucket automatically, since they were already grouping by `opponent_type` — no separate computation needed. `page_ships.py`'s deaths-by-ship table (`_wide_ship_table`) was generalized to take an explicit list of opponent types per table (kills stays NPC/Player only, since no kill-voucher event has a self-caused equivalent; deaths is now NPC/Player/Self-Accident) rather than hardcoding two columns, and gained a third "Self/accident deaths" column plus an updated title breaking out the self-inflicted share of the total.

**A second, more consequential misclassification came out of the same check.** `is_ship_combat()` (used by `combat_analysis.html`'s "every recorded ship-combat death"/overconfidence table) treats a *missing* `killer_ship` value as `True` by default — a default aimed at genuine ship-vs-ship losses where the field is simply absent from that particular export, not at the true no-antagonist-at-all case. Since a self-inflicted death's `killer_ship` is always missing (there's no killer to name a ship for), every one of those 12 events was being counted as a "ship-combat death," and could even trip the "overconfidence" flag for a non-combat ship — a collision or a fuel-scoop overheat being reported as if the ship got into a fight it wasn't built for. Fixed by excluding `opponent_type == "Self/Accident"` from `is_ship_combat` explicitly, on top of the existing vehicle-state and on-foot-killer checks. Confirmed the effect directly on the real database: the Combat Analysis page's ship-combat-death count dropped from 34 to **26** (of the 40 SHIP-state deaths total, 8 are self-inflicted and now correctly excluded from "combat"), and the deaths-by-ship table's own "40 genuine losses" total is unchanged (self-inflicted deaths were already being counted somewhere in that total before, just mislabeled as NPC) but now correctly reports 8 of the 40 as self/accident rather than combat.

**A redundant query removed along the way.** `deaths_by_ship`/`deaths_by_ship_summary` used to come from a second `Died` query (`death_rows`) that duplicated the exact ship/vehicle-state/opponent-type joins already computed for `died` (the Combat Analysis page's own dataframe, built earlier in the same function) — a second query doing identical work, purely because the two features were added in separate rounds. Removed; `deaths_by_ship`/`deaths_by_ship_summary` now build directly from `died` once its `opponent_type` column is computed, which also guarantees the two tables can never quietly drift apart on classification logic in a future change.

Verified via the same established pipeline as every prior round: full rebuild against the real 2,018,910-event database (Playwright: 0 JS errors on both `ship_profile_analysis.html`, still 9 divs, and `combat_analysis.html`, still 5 divs — only the underlying counts changed, not the figure count), confirmed the exact real-database numbers above by reading the raw `Died` JSON directly (not just trusting the rendered table), full rebuild against the synthetic fixture (which has zero `Died` events of any kind — renders "Deaths by ship: 0 genuine losses across 0 ships -- 0 of those were self-inflicted/accidental" cleanly, no `.xs()`/empty-index regression), and a re-run of the fit-vs-usage regression check confirming no change (same 3 flags for "Trade Baron," 0 for "Iron Fist"/"Long Rover"). Both changed files (`journal_deepdive.py`, `page_ships.py`) delivered to the user.

## Exploration-hypothesis-table round: discovery type x star type hit-rate crosstab

Follow-on to a conversational analysis, not a report feature, done in the same session: the user asked to investigate whether past discoveries of Earthlike/Water/Ammonia worlds, pristine (especially pristine metallic) rings, and biological finds correlate with anything observable from outside a system — star type in particular — to guide future exploration destination choices. The user then asked for one of those tables to become a real feature on the Exploration Deep Dive page, as a single combined crosstab: discovery type in the rows, star type (all visited) as columns, hit % at the intersection.

**System attribution via an ASOF join on primary-star arrival, not the existing `star_system`/`SystemAddress` fields.** The existing exploration code (used elsewhere on this same page) attributes events to a system via the raw `star_system` column or `SystemAddress`-keyed `addr_map`, but both are frequently absent from pre-2018-format journal events (~7–11% missing even on modern-ish events, worse on older ones) — material undercounting for a query meant to cover the full nine-year history. Built a `system_boundary` view instead from `FSDJump`/`Location`/`CarrierJump`'s own `StarSystem` field, and ASOF-joined every `Scan`/discovery event to the nearest-preceding boundary event by timestamp (the same idiom this tool already uses for ship and vehicle-state attribution) — full-history coverage regardless of which fields a given event happens to carry. The system's primary/arrival star is identified via `DistanceFromArrivalLS = 0.0` on its own `Scan` event. Hit a real DuckDB limitation combining this with a `json_each()` cross join for the ring array in one query ("Non-inner join on correlated columns not supported"); fixed by materializing the ASOF-joined ring scans into a `CREATE OR REPLACE TEMP TABLE` first, then running the array cross join as a separate, non-correlated query against that table.

**Two real bugs, both caught by the established screenshot-verification discipline rather than the JS-error/div-count check, which reported clean on both broken versions.**

1. **21 columns, taken from "all visited star types" too literally.** A first version gave every distinct star type its own column — 21 for the real database, most with only a handful of visits — which squeezed header text into unreadable overlap and made the table far too wide to read. A second attempt pooled star types below a visit-count threshold into an "Other" column, but most of the 21 types (including several giants, brown dwarfs, and white dwarfs) individually clear any reasonable threshold on this dataset, so the table stayed nearly as wide, and long internal class names like `K_OrangeGiant` still overflowed their header cells. Settled on a fixed whitelist instead: the 7 standard main-sequence classes (O, B, A, F, G, K, M) — the same breakdown `exploration-destination-hypothesis.md`'s own tables use — get their own column, and every other star type (giants, brown dwarfs, white dwarfs, T Tauri stars, neutron stars, black holes, and the like) pools into "Other" regardless of how often it was visited. Nothing visited is dropped from the underlying hit-rate math — "Other" still counts toward every percentage — but the column count is now fixed and legible rather than scaling with how many exotic star types the journal happens to contain. This is a real, explicit deviation from a strictly literal reading of "star types (all visited) as columns," worth surfacing directly: every visited star type is still represented in the table (via "Other" for the rare ones), just not each given a dedicated column, since a literal 21-column table proved unreadable in practice.
2. **A go.Table figure rendering a visible header over a completely empty body, with zero JS console errors either way.** A `go.Table`'s header/cell content is laid out inside whatever vertical space is left after the figure's own `height` and `margin.t` — a version that set a tall top margin (to fit a long caption) without growing the figure's height to match left less room than the table's actual content needed, and the body silently rendered with no visible rows. The underlying data was confirmed correct by printing the `star_type_hitrate` DataFrame directly in Python, outside the browser, ruling out a data bug before chasing a rendering one. Rather than fight `go.Table`'s height/margin coupling further (or the header-text-wrapping problems from bug 1, which a `go.Table` header cell handles poorly for anything longer than a couple characters), the table was rebuilt as a plain HTML `<table>` — one of `write_page()`'s `figs` list items can already be a raw HTML string, not only a plotly Figure (as long as `figs[0]` stays a real Figure, needed for the inline plotly.js bundle) — with the caption as ordinary HTML text above it. This sidesteps the whole class of go.Table sizing bug, since an HTML table sizes itself to its own content.

Both fixes verified together after rebuilding: Playwright JS-error/div-count check (0 errors; plotly-div count correctly dropped from 5 to 4 once the table stopped being a plotly figure, with a separate real `<table>` element count of 1), and a screenshot specifically of the new table and its caption confirming 8 legible columns (O/B/A/F/G/K/M/Other) and all 4 discovery-type rows fully visible — replacing an earlier screenshot that had shown both bugs clearly (a 14-column header with overlapping text, and a header with no visible rows beneath it). Also rebuilt against the synthetic fixture, which has too few high-value-planet/ring/bio finds to populate `star_type_hitrate` meaningfully: the existing `if not star_type_hitrate.empty` guard correctly skips the whole section rather than rendering a broken or misleading table (0 JS errors, section simply absent, as intended). ## File-collision self-healing: build_report.py recovers automatically from the "-1" download bug

The user hit the recurring file-naming-collision bug (see the standing project convention docs for the earlier manual diagnosis/fix) a second time in this same session: a re-delivered `.py` file landed on their machine as `journal_deepdive-1.py`/`page_exploration-1.py` instead of overwriting the plain-named file Python actually imports, so a rebuild silently kept running the stale version with no error of any kind. Diagnosed live via the device-bridge file tools (`device_list_dir`/`device_stage_files`), confirmed the `-1` files were byte-identical to what had been delivered, and fixed by `device_commit_files`-ing the current content over the stale plain-named files (`force: true`).

The user then asked for this to stop being a manual fix: "build in a check to perform for recurrence, and fixing." `build_report.py` now runs `_sync_stale_downloads()` as its very first step, before importing any of this tool's own modules (imports read whatever is on disk *right then*, so a repair has to happen first). For every `<module>.py` this tool ships, it looks for `<module>-<N>.py` siblings, and if any sibling (including the plain-named file itself) has a strictly newer mtime and different content than what's currently imported, copies that newest content over the plain-named file, then deletes every numbered sibling that now matches (and clears `__pycache__`, to avoid running stale bytecode after a sync). Prints exactly what it did (`[auto-fix]`/`[cleanup]`/`[notice]`) when there's something to report, and stays completely silent on an ordinary run with no collision. Only touches files this tool actually ships (`build_report.py`, `journal_common.py`, `journal_deepdive.py`, `journal_page_utils.py`, every `page_*.py`, and now `serve_report.py` below) — never a bare "-N" pattern match against unrelated files that might legitimately exist in the folder.

Running `build_report.py` printed the auto-fix message, removed the marker from the now-synced plain file, deleted the `-1` sibling and `__pycache__/`, and proceeded to build normally. A second run against an unmodified copy (no collision present) produced no extra output at all, confirming the check doesn't add noise to the common case. `build_report.py` was then delivered to the user, who confirmed on their own machine that overwriting the stale files (done directly via the device bridge in this instance, since the fix was needed immediately) got the rebuild picking up the new content.

## Tabbed-shell-UI round: replacing the multi-page site with one app (left tab bar + Refresh button)

Direct request: "I would like to recreate and improve the UI for this project. Currently we are using a very primitive html interface. I would like a multipanel UI with the sections behaving as tabs, with the tab bar either on top or on the left side of the screen. I would like that to stay visible while the content of the page is scrollable. I would also like a 'refresh' button that will rerun build_report.py and once that completes refreshes the page (returning to the tab on which the refresh was invoked). I want the browser to NOT cache any of the page data so a refresh will show the updated page as we add elements." A genuine architecture change rather than a page addition, so three decisions were confirmed with the user up front rather than assumed, since getting them wrong would mean redoing the whole shell: tab bar on the left (not top); running a small local server is acceptable (needed for Refresh to actually execute Python, since a bare `file://` page has no way to launch a subprocess); and the new tabbed UI fully replaces the old multi-page site rather than keeping both.

**Restructuring, without touching any `page_*.py` module's own logic.** Every page module already had the identical `build(data, out_dir)` signature and wrote its output via the shared `write_page()` helper, so the whole restructuring happened at the two integration points (`build_report.py`, `journal_page_utils.py`) rather than in any individual page: `build_report.py` now creates a `tabs/` subdirectory and passes that as `out_dir` to every `page_*.build()` call instead of the top-level output dir, so each existing page module writes its already-correct fragment into `tabs/` completely unaware anything changed; `write_page()` gained an `include_nav` parameter defaulting to `False`, dropping the old per-fragment top nav bar (now redundant — the shell's own sidebar replaces it) without deleting `nav_html()`/`NAV_LINKS`, which the shell itself now consumes directly as its canonical tab list. The former `build_index()` (the old top-level landing page) became `build_overview_tab()`, writing `tabs/overview.html` as just another tab instead of a separate top-level page.

**The shell itself (`build_shell()` in `build_report.py`, writing `index.html`).** A fixed-position left sidebar (tab buttons built from `NAV_LINKS` + a Refresh button) and a fixed-position main area holding one `<iframe>` per tab. Each tab's iframe is created (its `src` set) only the first time that tab is opened — not all 9 up front, which would mean loading nine ~4.5MB inlined-plotly.js documents on first paint — and then left in the DOM, just shown/hidden via CSS on later switches, so revisiting a tab is instant and keeps its scroll position (each iframe's own document scrolls internally; the sidebar itself never scrolls with it, satisfying the "tab bar stays visible while content scrolls" requirement directly from the layout, not from any special-cased CSS). The active tab is tracked in `location.hash` via `history.replaceState` (not `pushState`, so clicking through tabs doesn't spam browser history) — which is also how "return to the tab the refresh was invoked from" is satisfied for free: the hash survives an ordinary page reload, and the shell reads it back on load to pick the initial tab.

**No caching, three layers deep, not just one.** (1) `write_page()` now writes `Cache-Control`/`Pragma`/`Expires` no-store meta tags into every fragment's `<head>`. (2) `serve_report.py`'s handler overrides `end_headers()` to send the same no-store headers on every HTTP response, for every file, not just the shell. (3) Every iframe `src` carries a cache-busting `?v=<build-stamp>-<timestamp>` query string, combining the shell's own build time (so a rebuild always produces a fresh value) with the moment the tab is opened (so reopening the same tab in the same session-without-a-rebuild also bypasses any cache). Belt-and-suspenders deliberately, since the whole point of the Refresh button is trusting that what's on screen after it fires is actually new.

**`serve_report.py` (new file).** The piece that makes Refresh real rather than cosmetic: a small `ThreadingHTTPServer` wrapping `http.server.SimpleHTTPRequestHandler` (bound to the report's output directory via its `directory=` constructor argument), adding the no-cache headers above to every response and one extra route, `POST /api/rebuild`, which shells out to `python build_report.py <db> <out_dir>` as a subprocess (so it always runs the current on-disk code, the same as invoking it by hand would) and returns `{ok, log}` as JSON. The shell's Refresh button POSTs to that route, disables itself and shows a "Rebuilding..." status while waiting, then does a plain `location.reload()` on success (hash-preserved tab restore, per above) or shows the failure inline without reloading if the subprocess returned nonzero. Opening `index.html` directly (no server) still works as a read-only view — every fragment renders fine — but Refresh has nothing to talk to and says so ("couldn't reach the local server") rather than silently doing nothing.

**Verification, adapted for a UI-shaped change rather than a data-shaped one.** The existing Playwright JS-error/div-count check still applies (0 errors on load, and after clicking through every tab, against both the real and synthetic databases), but the more load-bearing checks here were interaction-based: driving the shell in a live browser to confirm clicking a tab actually loads the right fragment's content (checked by asserting the Exploration Deep Dive tab's iframe contains the star-hit-rate table's own heading, not just that some content loaded); confirming the sidebar visually stays in place while the active tab's content is scrolled deep past the fold (screenshotted mid-scroll specifically to catch a fixed-position layout bug that a static screenshot at scroll-position-zero couldn't have shown); and actually driving the full Refresh round-trip end to end in Playwright — click Refresh, wait through a real ~15–20s rebuild, and assert that the tab active after the resulting reload matches the tab active before clicking. `curl`-verified the `Cache-Control: no-store` header is genuinely present on every served response, not just written into the page source. Also re-ran the synthetic-fixture build against the new structure and clicked through all 9 tabs against it — clean, no JS errors, exercising the same "does this hold up on a much sparser database" discipline used throughout this project, just against the shell/tab-loading mechanism instead of a data computation this time.

Three files changed/added (`build_report.py`, `journal_page_utils.py`, `serve_report.py` (new)) plus `README.md`, all delivered to the user, with `README.md` updated to describe the new two-script (`build_report.py` + `serve_report.py`) workflow and to state plainly that opening `index.html` directly still works read-only but the Refresh button needs the server.

## Validation summary

- Headless-rendered (Playwright) every page after every change, not just checked for a clean exit — confirmed real SVG/chart-div content and zero JS errors each time, specifically against the real 2,018,910-event / 1,559-session database, not just synthetic data or a single spot-check.
- Ship attribution and fit-vs-usage logic re-validated against synthetic ground truth (three ships, non-overlapping behavioral evidence, time windows corrected so ASOF-join attribution can't bleed across ships) after every round of changes, to confirm unrelated changes didn't regress the data pipeline — exact match to ground truth every time, including after both the deep-dive and surface-activity rounds' `journal_deepdive.py` additions.
- Full report regenerated end-to-end against the real database as part of validation, confirming every fix holds at full scale, not just in synthetic tests.
- Sum-reconciliation (checking that a per-ship or per-category breakdown sums back to the same fleet-wide total computed independently) proved itself in the deep-dive round as a reliable way to catch subtler versions of a bug that a first fix and a first pass of testing both missed — worth using again for any future per-ship/per-category monetary or count breakdown.
- Tracing a handful of real event sequences by hand (not just reading field names) before writing an aggregation query, as done for the SRV/on-foot state machine, caught the Embark/Disembark dual-purpose (ship vs. SRV) semantics before any code was written around a wrong assumption — worth doing again whenever a new event type's exact state-machine behavior isn't already documented in this file.
- **From the persona-dialogue round**: any raw keyword/substring search over event text or field content (as opposed to querying a specific, known event type or field) gets its actual matched rows read before the count is reported as a finding, regardless of whether the count looks plausible — a large, plausible-looking hit count is exactly the case where a false positive is most likely to slip through unnoticed (Titanium-as-"Titan", `asp_scout`-as-"Scout", an NPC named "Firestorm", other players' carriers named "Kestrel" all looked like real signal until the actual rows were read). **This habit still needs to be actively re-applied to claims already sitting in a delivered document, not just to new findings** — the "Rigel" substring match (actually "Maidubrigel") sat uncorrected in a delivered doc through an entire subsequent round before a user correction on an unrelated point prompted re-checking it.
- **From the backstory-correction/aspirations round**: per-ship event attribution (ship = nearest-preceding `Loadout` in the same session) needs a vehicle-state check — was the player actually in that ship, or on foot/in an SRV launched from it, at the exact moment of the specific event — before being reported as "this ship did X," for any event type that can also occur on foot or in an SRV. The same round confirmed this generalizes beyond kill attribution: an ad hoc `ShipName`-grouped query (not routed through `journal_common.py`'s validated `ShipID`-based logic) silently dropped the Type-11 Prospector from a fleet inventory, because its name had been reused from an unrelated ship — any one-off diagnostic query written directly against the database needs the same `ShipID`-not-`ShipName` discipline, not just the pages that already go through the shared pipeline.
- **From the after-action-design round**: verified (by `Grep`, not by assumption) that no page module has a hardcoded wall-clock/current-date dependency that would silently misbehave as new journal files accumulate — confirming the pipeline is actually ready for the after-action/ongoing-monitoring use case, rather than just assuming the existing incremental-ingestion design covers it.
- **From the vehicle-state-fix round**: an "open risk" flagged in a prior round's notes ("worth checking whether the same gap affects other per-ship combat/usage numbers... not re-verified yet") is not the same as a closed one — it sat as a to-do item until directly chased down, at which point it turned out to be real and fleet-wide (18% of all combat-type events), not a minor edge case. Worth remembering: a documented-but-unverified gap should be treated as "probably still there" until actually re-checked, not "probably fine since nothing else was reported." Also: the synthetic regression fixture's very sparsity (one ship with any kills, zero with `Player`-type kills/deaths) is exactly what exercises edge cases the much-larger real database naturally papers over by having at least a few of everything — re-running it caught a real `.xs()`/`reset_index()` bug before the real-database build (which happened to have just enough ship/opponent-type combinations to route around it) ever revealed it.
- **From the self-inflicted-deaths round**: a classifier's catch-all fallback ("anything I don't recognize is category X") can silently absorb a genuinely distinct case rather than actually classifying it — `death_opponent_type()`'s `return "NPC"` fallback wasn't wrong for the cases it was written for (a `Died` event really does default to NPC-caused when nothing else fits, in most journal exports), but it also swallowed the one case that needed its own category, because nobody had checked what "nothing else fits" actually contained until asked to differentiate it. The same root habit as the vehicle-state gap: read every real example of an edge case before trusting a default clause to handle it correctly, especially one that's never actually been enumerated. Also: a "missing field defaults to True/combat" convention that's correct for one meaning of "missing" (data simply wasn't exported) can be wrong for another meaning of the same missing field (there was genuinely nothing to record) — the two need to be told apart explicitly, not merged under one default.
- **From the Session Spotlights round**: a long-lived function that accumulates many large intermediate DataFrames as live local variables (like `compute_deep_dive()`) can run a late-added full-table query into an out-of-memory kill even when that exact query is cheap in isolation — the fix isn't to make the new query smaller, it's to notice that an already-computed, already-in-memory dataframe can usually answer the same question via a pandas filter instead of a fresh DuckDB pass, and to prefer that by default for anything added late in this function from now on. Also reconfirmed, a third-plus time, that boolean-mask-filtering an already-empty DataFrame drops all its columns, not just its rows — worth treating as a standing rule for this codebase (explicit `.empty` check before filtering) rather than re-discovering it per round. And a reminder specific to `write_page()`: its inline-plotly.js-bundle requirement that `figs[0]` be a real `Figure`, not an HTML string, is easy to violate by accident when a page's most natural reading order puts a text/HTML block first — worth checking `figs[0]`'s type explicitly on any new page module, not just trusting that "the page rendered without a Python exception" means the JS loaded too.
- **From the exploration-hypothesis-table round**: a "give every distinct value its own column/row" instruction, taken literally, can produce something technically correct but genuinely unreadable once the real value count is much higher than expected (21 star types vs. an implicit assumption of a handful) — visual screenshot verification caught this even though the JS-error/div-count check reported clean, reconfirming that check alone is necessary but not sufficient. Deviating toward a fixed, legible column set (with an honestly-labeled "Other" pooling everything outside it) is a reasonable resolution, but it's a real deviation from the literal instruction and needs to be surfaced to the user as such, not silently substituted. Also: `go.Table`'s height/margin coupling has now caused a real empty-body bug once already (this round) on top of the general fiddliness noted elsewhere in this doc — for a simple data grid with no interactivity need beyond display, a plain HTML `<table>` (supported directly by `write_page()`'s `figs` list, as long as `figs[0]` stays a real Figure) sidesteps that whole bug class and is worth defaulting to over `go.Table` for future tabular additions to this tool.
- **From the file-collision self-healing round**: a bug that's been manually diagnosed and fixed once before is worth building a standing, self-running check for — rather than re-diagnosing it by hand every time it recurs — once the trigger condition is well enough understood to detect programmatically (here: a same-named sibling file with a newer mtime and different content). The self-check runs before any of this tool's own module imports specifically because the bug's effect (stale code silently running with no error) only matters at import time; verified by actually reproducing the bug end-to-end in an isolated copy rather than just reasoning about the fix in the abstract.
- **From the tabbed-shell-UI round**: a UI restructuring can often be done as a pure integration-layer change — routing existing, already-correct output through a new shell (`out_dir` becoming `tabs/`, plus one new parameter on the shared writer) — without touching any individual page module's own logic at all, as long as every page already goes through one shared, consistent interface (`build(data, out_dir)` + `write_page()`, established from the very first restructuring round at the top of this doc). Also: verifying a UI change well requires interaction, not just a static render check — the JS-error/div-count check alone would have missed a broken tab-switch, a sidebar that scrolled away with its content, or a Refresh button that didn't actually return to the originating tab; each of those needed a live click-and-observe Playwright pass, the UI-layer analog of the screenshot-over-text-extraction lesson from earlier rounds. And: three genuinely ambiguous, expensive-to-redo decisions (tab position, whether a local server is acceptable, whether to keep the old pages) were confirmed with the user before writing any code, rather than guessed at and possibly rebuilt from scratch after the fact.
