# Elite Dangerous Ship's Computer — Project Index

Start here. This project is exploring a Claude-based "Ship's Computer" for Elite Dangerous — reasoning over journal/Status.json/CAPI data to narrate, recommend, and (in one shipped case so far) manage config, alongside the user's existing toolset (EDMC, EDCoPilot, EDDiscovery, ED Materials Helper, EDDI, Inara).

## Reading order for a new session

1. **`design-principles.md`** — read this first, always. It's the constitution for anything that could touch the game itself: the automation-boundary rule, the three tests for whether a proposed feature crosses it, the recommendation-format pattern (stated action + stated criteria, always overridable, never self-executing) that differentiates this project from data-display tools like EDDiscovery, and a second, independent principle — **tedium is opt-in**: prefer lower-repetition paths when a recommendation has options, and state an honest effort/repetition estimate up front wherever real grinding (material farming, rank/permit thresholds, credit-grinding) is unavoidable. Every feature-shaped doc below is an application of this one.
2. **`tools-reference.md`** — the ecosystem survey: Journal/Status/CAPI as raw data sources, EDDN/EDSM/Inara/Spansh as aggregation networks, and the existing companion-tool landscape (EDMC as the likely ingestion path, COVAS:NEXT and EDDI as direct prior art). Read this to know what's already out there before proposing to build something new.
3. **`ui-guidelines.md`** — visual design tokens and audit of the ecosystem's actual look-and-feel, for any tool with a GUI (used already for EDCV Manager).

## Docs, by category

### Foundational
- **`design-principles.md`** — the automation boundary, the three tests, the recommendation-format pattern, and the tedium-is-opt-in principle (prefer low-repetition paths; state effort/repetition estimates honestly wherever grinding is unavoidable). Read first.
- **`engineering-practices.md`** — a build-process note, distinct from the above: once a capability is proven to work well, package it as a reusable skill/tool rather than re-deriving the approach each time (mind token/processing cost). The journal report tool (below) is now the clearest example of this in practice — validated building blocks (ship attribution, usage evidence) reused across pages and flagged for reuse in `ship-build-advisor.md`.
- **`tools-reference.md`** — third-party tool/API ecosystem survey (EDMC, EDDN, EDSM, Inara, Spansh, COVAS:NEXT, EDDI, and the long tail).
- **`ui-guidelines.md`** — Elite-Dangerous-style visual design system (tokens, audit, checklist) for anything with a GUI.

### Feature specs (applications of `design-principles.md`)
- **`exploration-triage-framework.md`** — classifying a system on arrival (known-uninteresting / unscanned / flagged-interesting), what's recommendable vs. automatable vs. must-stay-manual at each tier, and the route-sequencing sub-capability (with its open orbital-mechanics-vs-approximation question). See also `exploration-destination-hypothesis.md` below for a pre-arrival (not just on-arrival) triage signal not yet folded into this framework.
- **`surface-navigation-assist.md`** — planetary surface bearing/descent-angle/settlement-placement math. Notable as the cleanest case: pure computation, no automation-boundary question at all since it never issues a game input.
- **`ship-build-advisor.md`** — new-build recommendations, existing-build evaluation/"sweet spot" optimization, a sourcing shopping list, and permit-readiness checks. Built on `EDCD/coriolis-data`'s real numeric engineering-modifier data, plus `EDCD/coriolis`'s own MIT-licensed calculation code (`Calculations.js`/`Ship.js`) for the stacking/diminishing-returns math — confirmed reusable. Shopping-list sourcing redirects to EDDN, not Inara (see `inara-api-notes.md`); permit-status checking is confirmed unavailable from any known source, not just unresearched, so that feature is scoped down to reference-only. The journal report tool's fit-vs-usage table (below) already does half of Feature B (existing-build evaluation) using real usage data — the missing half is the Coriolis-based "what to swap to" math, still not built.
- **`inara-api-notes.md`** — research pass on Inara's developer API: what it actually covers (commander-data sync, no read-only market/outfitting/permit endpoints), the real rate limit (2 req/min, from the developer discussion board, not the formal docs), the whitelisting process, and a note that Inara's backend itself is closed-source (unlike EDMC/EDDN/Coriolis). Also carries relationship context worth keeping in mind: Inara's developer (Artie) has been financially supported by the user in the past, and any future integration should be pursued respectfully — a direct conversation before building, not building first and asking later.
- **`data-architecture.md`** — architecture for parsing the user's ~10 years of journal logs (1,559 files, ~1.18GB) into a queryable DuckDB database: local-file storage (no server, since none of our environments can durably host one), why a "hosted container as a web resource" doesn't work under Artifact CSP constraints, the hybrid events-table-plus-raw-JSON schema, idempotent incremental ingestion, lazy session-start consolidation instead of live-tailing, confirmed resilience to Frontier's ongoing game updates (new event types/fields absorbed without reprocessing, indexes added without re-ETL), and confirmation the approach is fully replicable as a plain script with no AI dependency for other players. Also documents a corrected assumption: a built database this size cannot live in this claude.ai Project (hard token-budget cap on the doc store) — its real home is the user's PC.
- **`journal-analysis-findings.md`** — build log for the first full run: 2,018,910 events parsed from all 1,559 files, 0 parse errors, 214 distinct event types, database delivered to `D:\Elite\journal.duckdb` on the user's PC (with reassembly commands/checksums, since it had to travel as split compressed parts). Initial findings on the motivating question: zero PowerPlay engagement, no evidence of actual CQC play, Thargoid contact is passive/incidental only (materials/scans, no combat evidence found in this pass).
- **`journal-visualization-tool.md`** — a standalone, no-AI-required tabbed local report (`journal_report_tool.zip`: a shell (`index.html`) with a left-side tab bar over one fragment per topic, plus `serve_report.py` for a live Refresh) built from `journal.duckdb`, structured for easy growth into a dashboard. **Gameplay Analysis** page: play-frequency/playtime by month, session-start heatmap, fleet-wide activity mix over time (with a precise transit-vs-deep-exploration split using the journal's real `ScanType` field), session-length distribution, dropdown event-type explorer. **Ship Profile Analysis** page: per-ship activity composition and time-series, plus a fit-vs-usage findings table flagging modules that look mismatched to a ship's demonstrated usage (e.g. a shield generator on a ship with zero combat history) — heuristic, every flag shows its raw evidence, explicitly not a replacement for the Coriolis-based optimal-fit math `ship-build-advisor.md` still needs. A real cross-ship data-misattribution bug was caught via synthetic ground-truth testing before this reached the user. Later rounds added **Play Patterns** (event tempo, session-length-vs-credits), **Combat Analysis**, **Economy Analysis**, **Exploration Deep Dive**, **Surface Activity** (SRV/on-foot time vs. active-mission correlation), and **Session Spotlights** (a per-session deep dive on the top 5 most lucrative sessions — what earned the credits, and whether it was carried-over/cashed-in value rather than earned that session) pages, plus an interview-style persona-dialogue round and its standing false-positive-verification habit, a file-collision self-healing round (`build_report.py` now auto-detects and repairs the recurring "-1 file" delivery collision on every run), and a full UI rearchitecture round (replacing the multi-page site with the tabbed shell + live-rebuild server described above) — see the doc itself for full writeups of each round.
- **`functional-requirements.md`** — a tech-stack-agnostic capture of everything the journal report tool must do (domain model: session/event-categorization/ship-attribution/vehicle-state rules; per-tab requirements for all 9 tabs; known correctness fixes that must not regress), written specifically so an in-flight rewrite onto a different stack (FastAPI + MySQL + live queries, replacing the current DuckDB/pandas/Plotly/static-HTML approach) can be checked against it rather than against the old code.
- **`exploration-destination-hypothesis.md`** — a data-derived, testable hypothesis for choosing future exploration destinations: primary (arrival) star spectral type is a usable pre-travel filter. Systems with A/F/G/K primary stars produce high-value planets (Earthlike/Water/Ammonia/Water giant), pristine rings (especially pristine metallic), and biological finds at 2-4x the rate of M dwarfs and 10x-to-near-zero versus brown-dwarf/T Tauri systems — visible via EDSM/galaxy map before ever traveling. Includes a within-system nuance (bio life and "flashy" planet classes are never the same body), an honest selection-bias caveat, and a concrete validation-trip plan (A/F/G/K batch vs. M-dwarf control batch) to test the pattern on fresh data rather than trust the retrospective numbers alone.
- **`cmdr-hussar-backstory.md`** — data-and-lore-grounded backstory for the player's in-game persona (CMDR James Hussar), cross-referencing the journal's hard data against the public Inara profile: the squadron's real Phiagre-based history (corrected from an earlier Rigel mixup — the correction independently confirmed by the data: the very first journal jump and dock, 3,653 direct Phiagre visits, 20,265 raw mentions, spanning 2017–2025), the Sovereign Justice Collective faction connection (69.6% of all bounty kills across nine years), the pre-journal explorer years from Inara's own logbook entries, and a working theory of the character's arc. A good worked example of the project's verification habit catching a real mistake on a second pass, not just hypothetically. Feeds directly into `future-aspirations.md`.
- **`future-aspirations.md`** — a curated, data-derived list of in-game goals: traveling to Rigel (Ghost Legion's new, post-relocation home system — never once visited in nine years, a stronger hook than the "closing a loop" framing an earlier pass mistakenly used) and contributing there; giving the six-system colony chain deliberate shape; a genuinely-rare-star-type exploration goal (several star types visited only once or twice ever); putting existing Guardian-tech investment (four FSD booster sizes already owned across the fleet) to actual use; and trying Operations with the squadron once at Rigel. Also documents what was deliberately left off the list (Powerplay, CQC) and why.

Not yet written up as their own docs, mentioned in conversation and worth formalizing if they get picked up: carrier multi-jump assist (currently a worked example *inside* `design-principles.md` rather than its own spec — promote it to a standalone doc if it gets built), mining limpet-swarm deployment (same situation), and an unrealized/at-risk credit warning (forewarn when substantial uncashed bounty/bond/exploration-data value is being carried into something risky — surfaced by the Session Spotlights page's #1 session; see `follow-up-todo.md`'s new "Live Gameplay Tooling" section for the full rationale).

For anything to do with ship engineering (blueprints, modifiers, materials), `EDCD/coriolis-data` (GitHub, JSON, actively maintained) is the go-to comprehensive resource — Frontier publishes nothing comprehensive of its own, and community wikis/Inara are navigation aids, not machine-readable datasets. See `ship-build-advisor.md`.

### EDCoPilot-specific (shipped work)
- **`edc-savedata-config.md`** — reference for what's genuinely user-configurable vs. pure telemetry in EDCoPilot's live save-data file (`Character:`, `shipNamePronounciation:`, `ExcludeDisplay:` vs. the ~280 telemetry prefixes to leave alone).
- **`edcopilot-eula-review.md`** — risk read on EDCoPilot's EULA: editing its save-data file and open-sourcing a companion tool are both low/low-moderate risk; avoid binary/exe inspection without asking the developer first.
- **EDCV Manager** (delivered as a working tool, not a project doc — see chat history for the zip and README) — the Windows GUI built from `edc-savedata-config.md`'s scope: searchable NPC/crew voice assignment, ship-name pronunciation, display-exclusion editing, with EDCoPilot-running detection forcing read-only mode.

## Where things stand / what's open

- CAPI is the identified path for any "participate in gameplay" feature that needs account-level data (market/outfitting/shipyard/fleet-carrier) or the few legitimate write actions (carrier commodity/service orders) — not yet built.
- EDDN was evaluated and ruled out as a target for a bespoke publisher: the user's EDMC already reports to EDDN/EDSM/Inara, so a new publish path would be redundant.
- Fleet carrier *unattended* multi-jump automation is explicitly ruled out (see `design-principles.md`); the *assisted* version (plan + tee up + notify, player fires every jump) is approved but not yet built.
- The journal report tool (above) is the project's most-iterated shipped capability so far — many real-use rounds (a blank-page rendering bug, ship attribution, a restructure + fit-vs-usage table, then successive new topic pages culminating in Surface Activity, a persona-dialogue round, Session Spotlights, a file-collision self-healing fix, and a full tabbed-UI rearchitecture) — and its ship-attribution/usage-evidence logic is now a validated building block worth reusing rather than re-deriving. **Currently mid-rewrite**: moving from DuckDB+pandas+Plotly+static-HTML to a FastAPI+MySQL+live-query+JS-frontend stack (see `functional-requirements.md` for what must be preserved).
- The persona/backstory/aspirations thread (above) is a distinct, lighter-weight track alongside the tool-building work: same underlying data and the same verification discipline, aimed at motivating what to actually go do in-game next rather than building anything.
- The exploration-destination-hypothesis thread (above) is a third, related track: same data and verification discipline again, this time aimed at a testable in-game targeting strategy rather than narrative motivation — its validation trip is still open (see `follow-up-todo.md`).
- No other feature spec here has moved to actual implementation yet, except the EDCoPilot-specific tooling above — everything else in "Feature specs" is design work ahead of a build decision.
